OpenFlyWheel System Book Design

Status: Approved Dogfood: Arceus-Inc Scope: Generic onboarding + System Book

OpenFlyWheel onboards a company or bounded production system, turns heterogeneous evidence into an auditable System Book, and supplies permission-filtered context to the agents the company already uses. No consumer topology is hardcoded in the product.

0. How you use it

You do not write a wiki. You connect the places work already happens, lock one system boundary, then let agents read from — and write evidence back into — a verified System Book.

You decide, lock, verify OpenFlyWheel scan, admit, extract, retrieve Agent Claude Code, Cursor, Codex, …

After lock — two loops, not a wiki

Write Evidence in

One sequence, left to right. GitHub PRs, issues, commits, and agent transcripts hit admission. Survivors become immutable episodes. SaO / grounded LLM emit proposals only. You verify. History is never deleted.

1 · source Source PR, issue, commit, transcript
2 · machine Admit fail-closed filter
3 · machine Episode immutable evidence
4 · extractor Proposal OFW writes this, not Cursor
5 · you Verify promote or leave open
6 · book Claim active What + How
Who writes the proposal? Not your coding agent. Greplica re-invokes Claude/Cursor after a session and that agent writes working-memory.proposal.json. OpenFlyWheel does not copy that. Your Claude Code or Cursor session is a source: it produces a transcript, which becomes an episode. A separate OpenFlyWheel extractor then writes the ClaimProposal.

Three proposers

  1. SaO — deterministic OFW code. Reads config, schemas, deps, tests. Preferred for U3/U4. No LLM.
  2. Grounded LLM job — OFW's leased background worker, not the session you were just in. Cites episode spans. Abstains if thin. Proposals only.
  3. You / an expert — answer a targeted question or run ofw claim propose. Still a proposal, never a direct claim row.

What the agent is allowed to do

  • Write a session transcript (episode).
  • Call claim_propose only as a hint; OFW still owns the row.
  • Never apply or activate its own claims.
  • Never get re-invoked by a hook to “update the Book” the Greplica way. Hook recursion is off during extraction.

Read Context out

An agent (or you) asks a question. Identity + ACL filter first. Active claims at the current pin come back as a compact Markdown packet: verified What/How, evidence, conflicts, and known gaps. No LLM on the read path in v0.

1 · agent Query book_context
2 · machine ACL identity first
3 · book Book active claims at pin
4 · machine Packet Markdown + gaps
5 · agent Prompt injected context

Concrete walkthrough — first dogfood week

Monday — stand up Arceus-Inc

You run ofw onboard, connect the GitHub org, install Claude Code and Cursor plugins. The scan proposes several boundaries (the OS, the harness, the org ledger, …). You lock one: the production-reachable Arceus stack, with U1–U7 coverage as the first KPI, and exclude secrets / personal forks.

Monday night — bootstrap

Repos, config, issues, and PRs become episodes. SaO fills a lot of U3/U4 (architecture, data flow). The coverage map shows U5–U7 mostly empty. You get a short list of expert questions: what was tried, what is failing, who owns on-call.

Tuesday — you work in Cursor as usual

You ask Cursor how Hippocampus memory is gated. The project rule calls book_context. You get verified claims plus file:line anchors — or an explicit gap if that How is not locked yet. When the session ends, a hook records it. A background worker may emit proposals. Nothing becomes gold until you or an owner verifies.

Later that week — the Book is the scoreboard

A teammate with a narrower identity asks the same question and gets a smaller packet. You pin Friday’s Book. Saturday’s ingest cannot change that pin. Coverage rises only when a required slot has verified evidence — not when the extractor dumps more U3 triples.

What “done” feels like An agent answers a cross-repo question from an evidence-backed packet, and the experiential holes (U5–U7) are visible as questions for you — not as fake completeness.

1. Objective

The System Book is not a search index, a wiki, or a dump of extracted triples. It is a versioned set of load-bearing claims about how a running system currently works. Every active claim has evidence, authority, freshness, and verification state.

Pavo's law A claim can be artifact-correct and still system-wrong. The unit of truth is the deployed system, not the isolated artifact.

2. Research basis

Pavo: Book schema

  • Locate and lock one system boundary before broad extraction.
  • Seven Essential Truths (U1–U7).
  • What + How are gold; Why is a probe.
  • Production-reachable behavior only.
  • SaO + grounded LLM extractors.
  • Machines own U3/U4; experts own U5–U7.

Hyper: write path

  • Connect to work already happening.
  • Admit, don't mirror everything.
  • Immutable episodes; structured facts.
  • derived_from, in_tension_with, supersedes.
  • Never auto-delete history.
  • Agents are bidirectional surfaces.
  • Hooks + MCP delivery.

OpenFlyWheel uses Hyper's write path inside Pavo's evidence and verification schema.

3. Non-goals for v0

  • No harness-improvement tournament.
  • No autonomous KPI optimization.
  • No Glean-style enterprise search.
  • No Graphiti or Neo4j dependency.
  • No Slack, Gmail, or company-wide firehose.
  • No LLM claim becomes active without proposal + verification.
  • No claim-count KPI inflated by U3/U4 extraction.
  • No agent-specific memory database.

4. Product boundary

Independent Python 3.11+ application. Repositories, agents, and SaaS tools are sources accessed through adapters. Core contracts are I/O-free. CLI, MCP, hooks, dashboard, connectors, and storage call the same application services.

The first workspace is Arceus-Inc. Its local manifest may name Arceus, dream, chorus, horizon, and lattice. Those names must never appear in reusable core code or generic tests.

5. Onboarding

ofw onboard is staged and resumable.

5.1 Workspace

  • Company / workspace name
  • Local or shared deployment
  • Administrators and identities
  • Default visibility and retention policy

5.2 Connect — Wave 0

GitHub

Organizations, repos, config, issues, PRs, commits, discussions. Collection inventory, timestamps, identities, permission metadata.

Agents

Claude / Claude Code, Cursor, Codex, OpenClaw, MCP for any other agent. Bidirectional: context in, session episodes out.

Expert notes are a first-class episode type from day one. Each connector reports collections, bootstrap/incremental capability, timestamps, identity fidelity, stable IDs, and freshness semantics.

5.3 Locate

Deterministic scans propose system boundaries, components, dependencies, shapes, owners, and visible KPIs. An LLM may summarize or rank; it cannot lock.

5.4 Lock

Human confirms boundary, purpose, shape, owners, first KPI, source authority, exclusions. Result: versioned WorkspaceManifest. No extraction before lock.

5.5 Bootstrap

  • Ingest approved source ranges.
  • Initial U1–U7 coverage map.
  • SaO before LLM extraction.
  • Targeted expert questions for weak U2/U5/U6/U7.
  • Explicit gaps, not fabricated coverage.

6. Processing pipeline

source item
  -> connector envelope
  -> admission policy
  -> immutable Episode
  -> SaO and/or grounded LLM extraction
  -> ClaimProposal + EvidenceAnchor
  -> dedupe + contradiction analysis
  -> authority / human verification
  -> active System Book Claim

6.1 Admission

Fail-closed. Reject junk, secrets, excluded paths. Audit-only record for rejects. Idempotent via source ID + content hash. Source content is evidence, not instructions.

6.2 Episodes

Immutable. Corrections = new episodes. Summaries never replace source text. ACL, event time, ingest time, checksum, source ref. Checkpoints advance only after successful episode transaction.

6.3 Extractors

SaO: constants, config, dependencies, schemas, guards, tests, metric defs.

Grounded LLM: atomic claims, exact spans, shape as prior not evidence, abstain, proposals only.

Expert: high-authority episode → proposal. No direct claim mutation.

6.4 Reconciliation

Neighborhood update with typed edges. Recency alone never determines truth. Authority, verification, production reachability, event time, and evidence agreement determine promotion.

8. Coverage KPI

section coverage = verified evidence-backed required slots / total required slots
overall coverage = macro-average(U1 .. U7 section coverage)

Raw claim count does not affect coverage. Requirements live in the manifest + shape ontology, not in product code.

9. Agent integration

System Book -> context packet -> agent prompt
agent session -> admission -> Episode -> ClaimProposal

9.1 Shared contract

Every platform plugin: safe install merge, session refs, hook normalization, transcript load/project, context delivery, write-back scheduling, diagnostics. Canonical events = metadata + human/agent text only.

9.2 Per-agent plugins

Greplica vs Hyper additions Greplica at 8ca8d2b: CLI + skills + hooks/rules for Claude, Cursor, Codex, Copilot, OpenCode, OpenHands, Factory Droid, Antigravity. No MCP, no OpenClaw. OpenFlyWheel adds MCP and OpenClaw inspired by Hyper.
  • Claude Code: skills + merged lifecycle hooks; Claude JSONL → canonical events.
  • Cursor: skills + always-applied project rule + hooks (rule drives context; hook records lifecycle).
  • Codex: skills + hooks.json; Codex-specific transcript adapter.
  • OpenClaw: new adapter after validating runtime API.
  • MCP: same Book services for desktop/web and hookless platforms.

CLI is canonical. Skills, rules, hooks, and MCP call the same application services.

9.3 Foreground / background

Foreground hooks: fast, best-effort, never block on background failure. Background worker: transcript → episode → proposals only. Hook recursion disabled during background extraction.

9.4 Operations

  • book_context(query, workspace, boundary, pin?)
  • book_get(claim_id, pin?)
  • coverage_gaps(section?)
  • episode_record(session_envelope)
  • claim_propose(what, evidence)
  • correction_record(claim_id, correction, evidence)

10. Retrieval

Deterministic v0 — no LLM on read path.

  1. Resolve identity and workspace
  2. ACL filter before ranking
  3. Active claims at pin/time
  4. SQLite FTS5 (+ optional embeddings)
  5. Direct evidence / conflict / supersession edges
  6. Compact Markdown packet

11. Storage and technology

Python 3.11+, Pydantic, SQLite/FTS5, Typer, FastAPI, MCP SDK, pytest, Ruff, strict mypy. Embeddings optional. All v0 tests pass offline without credentials.

13. Safety and error handling

  • Fail closed on missing ACL/identity
  • Never persist connector credentials in episodes or logs
  • Permission scope cannot widen
  • Prompt injection in sources = evidence text
  • Machine extraction cannot bypass proposal state
  • Idempotent connectors; checkpoint unchanged on failure
  • Background failure does not block foreground agent
  • Pins immutable; installers merge idempotently

14. v0 acceptance criteria

  1. No Arceus names in core code or generic tests
  2. ofw onboard discovers GitHub org and proposes boundaries
  3. Human can lock boundary, shape, owners, KPI, authorities, exclusions
  4. GitHub bootstrap + incremental ingest idempotent
  5. Claude Code + Cursor install without overwriting user config
  6. Both agents receive context and write session episodes
  7. Every active claim resolves to accessible evidence
  8. Contradictions inspectable; history never deleted
  9. Two identities → different packets for same query
  10. Historical pin unchanged after later ingestion
  11. Coverage per U1–U7 + macro-average
  12. Arceus dogfood: auditable Book with U5–U7 gaps explicit

15. First dogfood workspace

Arceus-Inc connects GitHub org + repos, Claude Code, Cursor, optional expert-note files. KPI: U1–U7 verified coverage. Success = cross-repo questions answered from evidence-backed packets; experiential gaps visible as expert targets.

16. Later surfaces

  1. Notion and Linear
  2. Slack after same-query / two-identity ACL test
  3. Drive, Gmail, Calendar, Granola
  4. LinkedIn only if people/outbound knowledge matters
